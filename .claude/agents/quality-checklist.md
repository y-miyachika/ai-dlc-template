# SubAgent/Skill 品質チェックリスト

このドキュメントでは、SubAgent/Skillの出力品質を確保するためのチェックリストを定義します。

## 共通チェックリスト

すべてのSubAgent/Skillの出力に適用：

### 形式面

- [ ] 出力ファイルが指定のディレクトリに配置されている
- [ ] ファイル名が命名規則に従っている（`{Intent番号}-{Unit番号}-{名前}.md`）
- [ ] Markdown形式が正しい（見出し階層、リスト、コードブロック）
- [ ] 日本語で記述されている（英語指定がない限り）

### 内容面

- [ ] 前提となるドキュメント（Intent、Units等）との整合性がある
- [ ] 曖昧な表現がない（「適切に」「必要に応じて」等を避ける）
- [ ] 具体的な数値・指標が含まれている（NFR関連）
- [ ] ユーザーの承認を得てから保存している

### トレーサビリティ

- [ ] 入力ドキュメントへの参照がある
- [ ] 出力ドキュメントへの参照がある（次のフェーズ）
- [ ] 変更履歴が記録されている（更新時）

## SubAgent別チェックリスト

### intent-definer（インテント定義）

**入力チェック**:
- [ ] タスク概要が提供されている
- [ ] 既存のIntentとの重複がない

**出力チェック**:
- [ ] ユーザーストーリーが As a / I want / So that 形式
- [ ] 受入基準が Given / When / Then 形式（BDD）
- [ ] NFRが具体的な数値で定義されている
  - パフォーマンス: 「レスポンス時間 < 1秒」等
  - 可用性: 「稼働率 99.9%」等
  - セキュリティ: 具体的な暗号化方式等
- [ ] リスクが識別され、対策が検討されている
- [ ] 成功指標が測定可能

**品質基準**:
| 項目 | 基準 |
|-----|------|
| ユーザーストーリー | 1つ以上 |
| 受入基準 | 3つ以上 |
| NFR | 2つ以上（パフォーマンス、セキュリティ） |
| リスク | 1つ以上 |

---

### units-decomposer（ユニット分解）

**入力チェック**:
- [ ] Intent定義が存在する
- [ ] Intent番号が正しい

**出力チェック**:
- [ ] 各ユニットの責務が1文で説明可能
- [ ] 境界が明確（含むもの/含まないもの）
- [ ] 依存関係が図示されている（Mermaid）
- [ ] 循環依存がない
- [ ] 実装順序が決定している

**品質基準**:
| 項目 | 基準 |
|-----|------|
| ユニット数 | 2〜7個（多すぎず少なすぎず） |
| 責務の記述 | 20文字以内 |
| 依存関係図 | 必須 |

---

### domain-designer（ドメイン設計）

**入力チェック**:
- [ ] Units定義が存在する
- [ ] 対象ユニットが指定されている

**出力チェック**:
- [ ] エンティティが識別されている
- [ ] 値オブジェクトが分離されている
- [ ] 集約とルートエンティティが定義されている
- [ ] ドメインルール（不変条件）が記述されている
- [ ] リポジトリインターフェースが定義されている
- [ ] ユビキタス言語が整理されている

**品質基準**:
| 項目 | 基準 |
|-----|------|
| エンティティ | 1つ以上 |
| 値オブジェクト | 適切に分離 |
| 集約 | 境界が明確 |
| ドメインルール | 各エンティティに1つ以上 |

---

### architecture-designer（アーキテクチャ設計）

**入力チェック**:
- [ ] Units定義が存在する
- [ ] ドメイン設計が存在する（推奨）

**出力チェック**:
- [ ] アーキテクチャパターンが選択されている
- [ ] 選択理由がトレードオフと共に記述されている
- [ ] NFRへの対応策が具体的
- [ ] コンポーネント図が作成されている（Mermaid）
- [ ] 外部API制約が考慮されている
- [ ] ADRが生成されている

**品質基準**:
| 項目 | 基準 |
|-----|------|
| ADR | 重要な決定に1つ以上 |
| コンポーネント図 | 必須 |
| トレードオフ分析 | 各パターンに1つ以上 |

---

### test-designer（テスト設計）

**入力チェック**:
- [ ] Intent定義（受入基準）が存在する
- [ ] ドメイン設計が存在する
- [ ] アーキテクチャ設計が存在する

**出力チェック**:
- [ ] BDD受入基準からテストケースが導出されている
- [ ] テストピラミッド（Unit/Integration/E2E）が定義されている
- [ ] 各テストケースにP0/P1/P2優先度が付与されている
- [ ] モック/スタブ戦略が決定している
- [ ] カバレッジ目標が設定されている

**品質基準**:
| 項目 | 基準 |
|-----|------|
| P0テスト | クリティカルパスを100%カバー |
| テストピラミッド比率 | Unit 70% / Integration 20% / E2E 10% |
| カバレッジ目標 | Line 80%以上 |

## Skill別チェックリスト

### api-generator（API生成）

**入力チェック**:
- [ ] services層が実装済み
- [ ] ユニット名が指定されている

**出力チェック**:
- [ ] HTTPエンドポイントが生成されている
- [ ] Zodスキーマが生成されている
- [ ] OpenAPI仕様が生成されている
- [ ] エラーハンドリングが実装されている

**品質基準**:
| 項目 | 基準 |
|-----|------|
| エンドポイント | CRUD操作を網羅 |
| バリデーション | 全入力にZodスキーマ |
| OpenAPI | 全エンドポイントを記述 |

---

### iac-generator（IaC生成）

**入力チェック**:
- [ ] アーキテクチャ設計が完了している
- [ ] ユニット名が指定されている

**出力チェック**:
- [ ] Terraformモジュールが生成されている
- [ ] 環境別設定（dev/stg/prod）がある
- [ ] 変数がパラメータ化されている
- [ ] セキュリティベストプラクティスが適用されている

**品質基準**:
| 項目 | 基準 |
|-----|------|
| 暗号化 | デフォルト有効 |
| IAM | 最小権限原則 |
| タグ | 全リソースに付与 |
| `terraform plan` | 成功すること |

---

### deploy-generator（デプロイ設定生成）

**入力チェック**:
- [ ] アーキテクチャ設計が完了している
- [ ] インフラ構成が検出可能

**出力チェック**:
- [ ] GitHub Actionsワークフローが生成されている
- [ ] デプロイスクリプトが生成されている
- [ ] 環境変数が文書化されている
- [ ] セキュリティ（Secrets管理）が考慮されている

**品質基準**:
| 項目 | 基準 |
|-----|------|
| 機密情報 | GitHub Secretsで管理 |
| 環境分離 | dev/staging/prodが分離 |
| ドキュメント | デプロイ手順が記述 |

## レビュープロセス

### セルフレビュー

SubAgent/Skill実行後、上記チェックリストでセルフレビューを実施：

```markdown
## セルフレビュー結果

**SubAgent**: intent-definer
**ユニット**: 001-unit1

### チェック結果
- [x] ユーザーストーリーが As a / I want / So that 形式
- [x] 受入基準が Given / When / Then 形式
- [x] NFRが具体的な数値で定義
- [ ] リスクの対策が不十分 → 追記が必要

### 改善アクション
1. リスク対策を追記
```

### ピアレビュー

重要なドキュメントは、ユーザーにレビューを依頼：

```
このインテント定義をレビューしてください：

1. ビジネス価値は明確ですか？
2. 受入基準は測定可能ですか？
3. NFRは現実的ですか？
4. 見落としているリスクはありますか？
```
