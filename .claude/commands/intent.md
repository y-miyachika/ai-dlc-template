## AI-DLCにおけるインテントとは

**インテント（Intent）**は、ビジネス目標、機能、または技術的な成果（例：パフォーマンスのスケーリング）など、達成すべきことをカプセル化する高レベルのステートメントです。

これは、AI駆動の分解を実行可能なタスクに行い、人間の目標とAI生成の計画を調整するための出発点として機能します。

---

## ステップ1: インテントの明確化（会話の逆転）

AI-DLCでは、**AIが会話を主導**します。まず、以下の質問でインテントを明確化してください：

### 必須質問（4つ）

1. **主要なユーザーは誰ですか？**
   - 開発者、デザイナー、エンドユーザー、プロダクトオーナー、その他
   - 例: 「開発者が主要ユーザーです」

2. **どのようなビジネス成果を達成したいですか？**
   - 開発効率の向上、品質改善、新機能の提供、技術的負債の解消、コスト削減、等
   - 例: 「開発効率を向上させ、手動作業を削減したい」

3. **制約条件はありますか？**
   - 時間制約（デッドライン）
   - 技術的制約（既存システムとの互換性）
   - リソース制約（トークン制限、メモリ制限）
   - 依存関係（他チームの成果物に依存）
   - 例: 「トークン使用量を5000以内に抑える必要がある」

4. **成功の定義は何ですか？**
   - 測定可能な指標（定量的）
   - 例: 「ビルド時間が10秒以内」「エラー率が1%未満」「ユーザー満足度80%以上」

**重要**: これらの質問への回答を得てから、次のステップに進んでください。

## 3. ユーザーストーリー（User Stories）

### ストーリー1: [タイトル]

```
As a [ユーザータイプ]
I want [機能・目標]
So that [ビジネス価値・理由]
```

**受入基準（Acceptance Criteria - BDD形式）**:

```gherkin
Scenario: [シナリオ名]
  Given [前提条件]
  When [アクション・操作]
  Then [期待される結果]
  And [追加の期待される結果]
```

**Example**:
```gherkin
Scenario: REST APIレスポンスの最適化
  Given 100階層のネストされたデータが存在する
  When データ取得APIを実行する
  Then レスポンスサイズが5KB以内である
  And データの精度が従来版と同等である
```

**チェックリスト形式の補足**:
- [ ] 基準1: 具体的で測定可能な条件
- [ ] 基準2: テストで自動検証可能な条件
- [ ] 基準3: ユーザーが価値を実感できる条件

**優先度**: High / Medium / Low

**見積もり**: Simple / Medium / Large

## 5. リスクレジスター（Risk Register）

| ID | リスク | 影響度 | 発生確率 | 対応策 | 責任者 |
|----|-------|--------|---------|--------|--------|
| R-001 | [技術的リスク1] | High | Medium | [対応方法] | [担当者] |
| R-002 | [依存関係のリスク] | Medium | High | [対応方法] | [担当者] |
| R-003 | [スケジュールリスク] | High | Low | [対応方法] | [担当者] |

**リスク影響度の定義**:
- **High**: プロジェクト全体に影響、リリース遅延の可能性
- **Medium**: 一部機能に影響、回避策で対応可能
- **Low**: 軽微な影響、短時間で解決可能

**発生確率の定義**:
- **High**: 70%以上の確率で発生
- **Medium**: 30-70%の確率で発生
- **Low**: 30%未満の確率で発生

## 注意事項（AI-DLC原則）

### 1. 会話の逆転
- **AIが質問を主導**し、人間が回答する
- 勝手に推測せず、必ず4つの質問を行う

### 2. 損失関数
- 早期に曖昧さを解消することで、下流の無駄な作業を防ぐ
- 受入基準は測定可能に（テストで検証できる）

### 3. コンテキストメモリ
- すべてのアーティファクトを永続化
- 後からAIが参照できるように詳細に記録

### 4. 段階的詳細化
- インテント → ユニット → ドメイン → コード
- 各ステップで人間の承認を得る

### 5. トレーサビリティ
- 成功指標とユーザーストーリーの対応を明確に
- リスクと対応策の紐づけ

## ベストプラクティス

### ユーザーストーリーの書き方
```
✅ 良い例:
As a 開発者
I want REST APIレスポンスのデータサイズを90%削減したい
So that Claude Codeのコンテキスト制限に引っかからずに大きなデザインを変換できる

❌ 悪い例:
REST APIを改善する
```

### 受入基準の書き方（BDD形式）
```
✅ 良い例（Given/When/Then形式）:
Scenario: データサイズ削減の検証
  Given 100階層のネストされたデータが存在する
  When データ最適化APIを実行する
  Then レスポンスサイズが5KB以内である
  And データの精度が従来版と同等である
  And エラー発生時に適切なフォールバック処理が動作する

✅ 良い例（チェックリスト形式でも可）:
- [ ] 100階層のネストデータをレスポンスサイズ5KB以内で取得できる
- [ ] データの精度が従来版と同等である（差分率5%以内）
- [ ] エラー発生時に適切なフォールバック処理が動作する

❌ 悪い例（測定不可能・曖昧）:
- [ ] うまく動く
- [ ] トークンが少なくなる
- [ ] 速くなる
```

### NFRの書き方
```
✅ 良い例:
| パフォーマンス | API応答時間 | 3秒以内 | 実測 | High |

❌ 悪い例:
| パフォーマンス | 速くする | できるだけ | - | - |
```

## 従来の `/backlog` との違い

| 項目 | `/backlog`（従来版） | `/intent`（AI-DLC準拠版） |
|-----|---------------------|------------------------|
| **構造** | シンプル | 体系的・詳細 |
| **質問** | なし | AIが4つの質問を主導 |
| **ユーザーストーリー** | 自由記述 | As a/I want/So that形式 |
| **NFR** | なし | 詳細な表形式 |
| **リスク** | 補足事項に含む | リスクレジスターで体系化 |
| **成功指標** | なし | 定量的・定性的指標 |
| **保存先** | `docs/backlog/` | `docs/intents/` |

**使い分け**:
- **シンプルなタスク**: `/backlog` で十分
- **複雑な機能・重要なタスク**: `/intent` を推奨
- **学習・比較**: 両方を試して違いを体感
