# アーキテクチャ設計（AI-DLC準拠）

引数として受け取ったユニット名をもとに、NFRを考慮したアーキテクチャ設計を行います。

## 入力内容
{{ARGS}}

---

## アーキテクチャ設計とは

AI-DLCにおける**論理設計フェーズ**です：
- NFR（非機能要件）をどう実現するか
- アーキテクチャパターンの選択
- トレードオフ分析
- ADR（Architecture Decision Record）の作成

**目的**: ドメインモデルを実装可能なアーキテクチャに落とし込む

---

## 動作フロー

### ステップ1: 前提情報の収集

以下のドキュメントを読み込む：

1. **インテント/Backlog**
   - `docs/intents/[番号]_*.md` または `docs/backlog/[番号]_*.md`
   - NFR（非機能要件）を確認

2. **ユニット分解**
   - `docs/units/[番号]_units.md`
   - 対象ユニットの責務、依存関係を確認

3. **ドメイン設計**
   - `docs/design-artifacts/domain/[番号]_[ユニット名]_domain.md`
   - ドメインモデル（エンティティ、集約等）を確認

---

### ステップ2: NFR分析

**NFRカテゴリごとに要件を整理**:

| カテゴリ | 要件 | 目標値 | 優先度 |
|---------|------|--------|--------|
| パフォーマンス | API応答時間 | 3秒以内 | High |
| スケーラビリティ | 同時接続数 | 100件 | Medium |
| 可用性 | 稼働率 | 99.9% | High |
| セキュリティ | 脆弱性対策 | OWASP準拠 | High |
| 保守性 | コードカバレッジ | 80%以上 | Medium |

**重要**: 優先度Highの要件はアーキテクチャ選択の制約となる

---

### ステップ3: アーキテクチャパターンの候補列挙

**一般的なパターン**:
- レイヤードアーキテクチャ（Layered）
- ヘキサゴナルアーキテクチャ（Ports & Adapters）
- クリーンアーキテクチャ（Clean Architecture）
- イベント駆動アーキテクチャ（Event-Driven）
- マイクロサービスアーキテクチャ（Microservices）
- サーバーレスアーキテクチャ（Serverless）

**候補を3つ程度に絞る**（このユニットに適したもの）

### ステップ5: 推奨オプションの決定

**評価基準**:
1. **NFR適合度**: High優先度のNFRを満たすか？
2. **実装コスト**: 現実的な期間で実装可能か？
3. **リスク**: 許容できるリスクレベルか？
4. **保守性**: 長期的に保守しやすいか？

**推奨理由を明確に**:
```markdown
## 推奨: オプションB

**理由**:
1. パフォーマンス要件（3秒以内）を満たす唯一のオプション
2. 実装コストはMediumで現実的
3. リスクは許容範囲内
4. 将来の拡張性も確保

**トレードオフの受容**:
- 初期実装が複雑になるが、NFR達成のため必要
- テストコード量が増えるが、品質保証のため必要
```

## ベストプラクティス

### 1. NFR駆動

**良い例**:
```
NFR: API応答3秒以内
  ↓
パターン選択: 段階的取得アーキテクチャ
  ↓
実装: depth指定、部分取得、キャッシュ
```

**悪い例**:
```
パターン選択: 一括取得（シンプル）
  ↓
NFR未達: 10秒かかる（要件違反）
```

### 2. トレードオフの明示

**良い例**:
```
採用: オプションB（段階的取得）
トレードオフ:
- 複雑性が増す（許容）
- 初期実装コスト高（NFR達成のため必要）
```

**悪い例**:
```
採用: オプションA（シンプル）
理由: 実装が簡単
（NFRへの言及なし）
```

### 3. 将来の拡張性

**考慮すべき点**:
- 新しいコンポーネントの追加が容易か？
- NFRの変更に対応できるか？
- 技術スタックの更新が可能か？

## AI-DLC原則との対応

| 原則 | 実装方法 |
|-----|---------|
| **損失関数** | NFR未達を早期検出（設計段階で） |
| **段階的詳細化** | ドメインモデル → アーキテクチャ → 実装 |
| **設計技術の統合** | DDD原則を保ちつつアーキテクチャ選択 |
| **トレーサビリティ** | NFR → アーキテクチャ選択 → ADR |

---

## トラブルシューティング

### NFRが曖昧な場合

**対処**:
1. `/intent` または `/backlog` を確認
2. NFRが不足していれば、ユーザーに確認
3. 典型的なNFR（パフォーマンス、セキュリティ等）を推測せず、明示的に確認

### 複数のNFRが競合する場合

**対処**:
1. 優先度を確認（High/Medium/Low）
2. ステークホルダーに確認
3. トレードオフを明示してユーザーに選択を求める

### ドメイン設計が未完了の場合

**対処**:
```bash
# 先にドメイン設計を実施
/design-domain [ユニット名]

# その後にアーキテクチャ設計
/design-architecture [ユニット名]
```
