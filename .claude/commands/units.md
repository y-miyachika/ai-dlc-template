# ユニット分解（AI-DLC準拠）

このコマンドは**Units Decomposer SubAgent**を使用して、インテントをユニットに分解します。

## SubAgentについて

`units-decomposer` SubAgentは、DDD（ドメイン駆動設計）原則に基づき、**疎結合・高凝集**のユニットに分解する専門SubAgentです。

**DDD原則**: サブドメイン、境界コンテキスト、ユビキタス言語を活用

詳細は `.claude/agents/units-decomposer/README.md` を参照してください。

---

## 入力内容

引数として以下のいずれかを受け取ります：
- インテント番号（例: `047`）
- 省略時は最新のインテント

```
{{ARGS}}
```

## SubAgent起動

以下を実行します：

1. **インテントの読み込み**: `docs/intents/{Intent番号}_{Intent名}/intent.md` から読み込み
2. **ドメイン分析**: サブドメイン、境界コンテキスト、技術的境界を特定
3. **ユニット分解**: 疎結合・高凝集の原則でユニットを定義
4. **依存関係の可視化**: ユニット間の依存関係を図示
5. **実装順序の推奨**: 依存関係、ビジネス価値、リスクを考慮
6. **ユーザー承認**: 分解案を提示し、承認を得る
7. **ファイル保存**: `docs/intents/{Intent番号}_{Intent名}/units.md` に保存

## SubAgent処理の詳細

SubAgentは `.claude/agents/units-decomposer/prompt.md` に定義された手順に従って処理を実行します。

**主要な処理**:

1. ドメイン分析（DDD観点）
   - サブドメインの特定（Core/Supporting/Generic）
   - 境界コンテキストの特定
   - 技術的境界の特定

2. ユニット分解の原則適用
   - 疎結合（依存関係の最小化）
   - 高凝集（関連機能のまとめ）
   - チーム規模、デプロイ単位を考慮

3. ユニット定義の生成
   - 責務、インターフェース、依存関係
   - 実装スコープ（Lambda Handlers含む）
   - NFR割り当て、リスク評価

**テンプレート詳細**: `.claude/agents/units-decomposer/prompt.md` を参照

## 分解の種類（規模に応じて選択）

### 小規模プロジェクト（単一ドメイン）
**技術レイヤー分解**を採用：
- フロントエンド / バックエンドAPI / バッチ処理 / 共通基盤
- 例：コミット可視化ツール、社内ダッシュボード、単機能アプリ

### 中〜大規模プロジェクト（複数ドメイン）
**DDDサブドメイン分解**を採用：
- Core Domain / Supporting Domain / Generic Domain
- 例：ECサイト（商品管理、注文管理、決済、配送）

### 判断基準
- ビジネスドメインが1つ → 技術レイヤー分解
- ビジネスドメインが複数 → サブドメイン分解
- 迷ったらユーザーに確認

### 分解結果の明示
ユニット一覧の冒頭に以下を記載：
```
**分解の種類**: 技術レイヤー分解
**理由**: 単一ドメイン（〇〇）のため
```

## ユニット分解の原則

### 疎結合（Loose Coupling）
- ユニット間の依存関係を最小化
- インターフェースを通じた通信
- イベント駆動アーキテクチャの活用

### 高凝集（High Cohesion）
- 関連する機能を1つのユニットにまとめる
- 単一責任の原則（SRP）
- 変更理由が同じものをまとめる

### サブドメイン分類（DDDサブドメイン分解の場合）
- **コアドメイン**: ビジネスの競争優位性
- **サポートドメイン**: コアを支える機能
- **汎用ドメイン**: 既製品で十分な機能

---

## 実装順序の決定

### 順序決定の2つのアプローチ

#### 1. 価値検証優先（推奨）
**ステークホルダーに早く見せてフィードバックを得る**

```
shared-domain（型定義のみ）→ UI → API → バックエンド処理
```

**向いている場合：**
- 要件の不確実性が高い
- PO/ステークホルダーとの合意形成が重要
- 新規プロダクト、MVP

**メリット：**
- 早期にUIを見せてフィードバック取得
- 「要件の誤解」を早く検出（AI-DLCの損失関数）
- 手戻りリスクを減らせる

#### 2. 技術依存順
**依存関係の上流から順に実装**

```
shared-domain → バックエンド処理 → API → UI
```

**向いている場合：**
- 技術的不確実性が高い（外部APIの挙動が不明など）
- インフラが複雑でDB設計が先に必要
- 社内ツールで要件が明確

### 注意点

- **型定義（shared-domain）は先に決める**: どちらのアプローチでも、UIとAPIの契約（データ構造）を先に定義
- **モックで代替可能**: バックエンドが未実装でもUIはモックデータで開発可能
- **DDDの「ドメインから作る」はユニット内の話**: 各ユニット内でドメイン層→インフラ層→ハンドラーの順

### ユーザーへの確認

実装順序を提示する際、以下を確認：
```
実装順序を決定します。どちらのアプローチを採用しますか？

1. 価値検証優先（推奨）: UI→API→バックエンド
   - 早期にステークホルダーへ見せてフィードバックを得る

2. 技術依存順: バックエンド→API→UI
   - 技術的不確実性が高い場合に採用
```

## 注意事項

1. **過度な分割を避ける**: マイクロサービスの罠（Nanoサービス）に注意
2. **共通機能の抽出**: 複数ユニットで使われる機能は共有ライブラリ化
3. **境界コンテキストの尊重**: DDDの境界コンテキストを意識
4. **段階的な分割**: 最初は粗く分割し、必要に応じて細分化
5. **チームの能力を考慮**: 技術的に実現可能な分割か確認
