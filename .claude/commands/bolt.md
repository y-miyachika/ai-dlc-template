# ボルト実行（AI-DLC準拠）

引数として受け取ったユニット番号をもとに、**高速反復サイクル（Bolt）**を実行します。

## 入力内容
{{ARGS}}

---

## Boltとは

AI-DLCにおける**最小の反復サイクル**です：
- 1つのユニット、または複数のユーザーストーリーを実装
- 設計→実装→テストを1サイクルで完結
- 各ステップで人間の承認を得る
- 時間スケール：数時間〜数日

---

## 動作フロー

### ステップ1: テスト設計の確認（TDD統合）✨NEW

1. `docs/design-artifacts/tests/[番号]_[ユニット名]_test_design.md` が存在するか確認
2. **存在しない場合**: `/design-test` 相当の処理を実行
   - 受入基準（BDD）をテストケースに変換
   - テストレベル分類（Unit/Integration/E2E）
   - TDDサイクル計画の作成
   - ユーザーにテスト設計を提示
3. **存在する場合**: 既存テスト設計を読み込み

---

### ステップ2: 実装計画の確認

1. `docs/plans/[番号]_plan.md` が存在するか確認
2. **存在しない場合**: `/plan` 相当の処理を実行
   - 既存コード構造を確認
   - 実装手順を詳細化（**テスト設計を参照**）
   - ユーザーに計画を提示
3. **存在する場合**: 既存計画を読み込み

---

### ステップ3: ユーザー承認

計画内容を提示し、実装開始の承認を得る：

```
以下の計画で実装を開始します。よろしいですか？

## 実装計画サマリー
- ユニット: [名前]
- 見積もり: [Simple/Medium/Large]
- 主要タスク: [リスト]

承認する場合は「はい」、計画を修正する場合は具体的な指示をください。
```

---

### ステップ4: TDDサイクル実行（Red → Green → Refactor）✨NEW

承認後、以下をTDDサイクルで実行：

#### Phase 1: Red（失敗するテストを書く）

1. **テストファイル作成**
   - テスト設計を参照し、テストコードを生成
   - `tests/[ユニット名]/[機能名].test.ts`
   - BDD形式（Given/When/Then）でテストケースを記述

2. **テスト実行（失敗確認）**
   ```bash
   pnpm test [テストファイル]
   ```
   - すべてのテストが失敗することを確認
   - 失敗理由が期待通りか確認（実装がないため）

#### Phase 2: Green（最小限の実装で通す）

1. **TodoList作成**
   - テストを通すための最小限のタスクを抽出
   - 優先順位順に並び替え

2. **段階的実装**
   - 1タスクずつ実装
   - 各タスク完了後にテスト実行
   - テストが Green になるまで実装

3. **テスト実行（成功確認）**
   ```bash
   pnpm test [テストファイル]
   ```
   - すべてのテストが通ることを確認

#### Phase 3: Refactor（リファクタリング）

1. **コード品質改善**
   - 重複コードの削除
   - 関数の分割・統合
   - 命名の改善

2. **Lint/ビルド確認**
   ```bash
   pnpm lint
   pnpm build
   ```
   - エラーがあれば修正

3. **テスト実行（回帰確認）**
   ```bash
   pnpm test
   ```
   - リファクタリング後もテストが通ることを確認

4. **完了報告**
   - 実装内容のサマリー
   - 変更されたファイル一覧
   - テストカバレッジレポート
   - 次のステップ提案

---

### ステップ5: 次のステップ提案

実装完了後、以下を提案：

- [ ] 他ユニットの実装（依存関係に基づく）
- [ ] E2E/Integrationテストの追加
- [ ] ドキュメント更新
- [ ] git commit（ユーザーに確認）

## 従来版との違い

| 項目 | `/plan` + `/apply` | `/bolt` |
|-----|-------------------|---------|
| **実行モード** | 2段階（計画→実装） | 1サイクル（統合） |
| **承認タイミング** | 計画後、実装前の2回 | 計画後の1回 |
| **用途** | 慎重に確認したい | 高速反復したい |
| **時間** | 柔軟（中断可能） | 数時間で完結 |

---

## 使い分けガイドライン

### `/plan` + `/apply` を使う場合

- 計画をじっくり検討したい
- 計画と実装のタイミングを分けたい
- 複雑な実装で段階的確認が必要

### `/bolt` を使う場合

- 高速に反復したい
- ユニットのスコープが明確
- AI-DLC準拠のワークフローを実践したい

---

## 注意事項

- **人間の承認は必須**: 実装開始前に必ず承認を得る
- **git commitは手動**: 自動コミットしない（ユーザーに確認）
- **エラー時の対応**: エラーが発生した場合は即座に報告し、対応を相談

---

## AI-DLC原則との対応

| 原則 | 実装方法 |
|-----|---------|
| **会話の逆転** | 計画を提示し、承認を得る |
| **損失関数** | TDDで早期に欠陥を検出（Red → Green） |
| **コンテキストメモリ** | テスト設計・計画・実装結果をdocs/に永続化 |
| **段階的詳細化** | BDD受入基準 → テスト → 実装 |
| **ステージ最小化** | テスト設計→計画→TDD実装を1サイクルで |
